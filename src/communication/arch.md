# Communication Package — Architecture

## Purpose

The `communication` package provides a transport-agnostic abstraction over
inter-process communication. Business logic in other packages depends only on
the concepts defined here — not on rclcpp or any specific transport.

When a new transport (shared memory, MQTT, I2C …) is added, the node code stays
unchanged. Only a new backend class implementing the app concepts is needed.

---

## Communicatable Data — the one fixed constraint

All data flowing through this system **must be a ROS2 interface type** (messages
generated by rosidl from `.msg` / `.srv` files). This is an intentional
architectural constraint, not an accident of the ROS backend.

- Future backends (MQTT, shared memory, serial …) will receive ROS2-shaped data
  and handle serialization/deserialization internally.
- New message/service types belong in packages under `src/interfaces/`.
- This constraint is **not enforced by a C++ concept** — rclcpp will produce a
  clear compiler error if a non-ROS2 type is used. It is enforced by convention
  and documented here.

---

## Concept Hierarchy

All contracts are expressed as C++20 concepts in `Concepts.hpp`.
Nothing uses inheritance; concept satisfaction is verified at compile time.

### Call-site concepts (one-param, self-describing)

The key design principle: each adapter type **carries its associated data type**
as a nested alias. The caller does not need to re-specify the type when checking
these concepts — the type is embedded in the adapter itself.

```
Publisher<T>     T::MessageType — the message type this publisher handles
                 T::Publish(const MessageType&) -> STATUS

Subscriber<T>    T::MessageType
                 T::StartHandler(Callback<MessageType>) -> STATUS

Client<T>        T::ServiceType — the service type this client handles
                 T::WaitForService(nanoseconds) -> bool
                 T::Request(const ServiceType::Request&, nanoseconds)
                     -> optional<ServiceType::Response>
                 T::AsyncRequest(req, timeout, responseCallback, timeoutCallback)
                     -> STATUS

Service<T>       T::ServiceType
                 T::Respond(const ServiceType::Request&) -> ServiceType::Response

Streamer<T, StreamT>   T::StartStream / StopStream / Send(StreamT)
Audience<T, StreamT>   T::JoinStream(Callback<StreamT>) / LeaveStream
```

These are applied at the **call site** (in node code, or in backend
`static_assert`s) where the specific message/service type is already known.

### Direction of constraint

```
Node ──────────────────────────────────────────────────────►
  decides MSG when it calls GetPublisher<MSG>()
  the returned RosPublisher<MSG> stamps MSG as its MessageType

Publisher ─────────────────────────────────────────────────►
  carries its own type information (MessageType alias)
  knows what it can publish

App ◄──────────────────────────────────────────────────────
  asks: "Is this Publisher self-aware? Can it publish its own type?"
  does NOT ask: "Can this Publisher handle type X?"
  the app is type-agnostic at the management level
```

This keeps the app layer transport-agnostic: it manages publisher/client handles
without ever needing to know what data type they carry.

### App-management concepts (one-param, shape-only)

These describe the **management API** of a communication backend — how to create,
delete, and retrieve channels. They do not constrain which data types are handled.

```
MessengerApp<T>        Login / Logout
                       CreatePublisher<MSG> / DeletePublisher / GetPublisher<MSG>
                       CreateSubscriber<MSG> / DeleteSubscriber
                       GetPublisher<MSG> must return shared_ptr<P>
                         where Publisher<P> holds (P is self-describing)

CommunicatorApp<T>     MessengerApp<T> +
                       Setup(argc, argv)
                       CreateClient<SRV> / DeleteClient / GetClient<SRV>
                       CreateService<SRV> / DeleterService
                       GetClient<SRV> must return shared_ptr<C>
                         where Client<C> holds

StreamerApp<T>         Login / Logout
                       CreateStream<T> / DeleteStream
                       JoinStream<T> / LeaveStream

FullCommunicatorApp<T> CommunicatorApp<T> && StreamerApp<T>
```

### Probe types in app concepts

`MessengerApp<T>` and `CommunicatorApp<T>` verify template-method shapes using
**real ROS2 types as probes**:

- `std_msgs::msg::Empty` — probe for publisher/subscriber methods
- `std_srvs::srv::Trigger` — probe for client/service methods

These are not arbitrary choices. Every communicatable type in this system is a
ROS2 interface type (see above), so `Empty` and `Trigger` are accurate
architectural representatives. `Concepts.hpp` includes their headers intentionally.

### No CommunicatorInterface concept

There is exactly one `Communicator` class. No other type in the system acts as a
switchboard. A concept that verified `Communicator` against itself would be
circular and provide no value. `Communicator`'s template methods are constrained
directly with the app concepts above.

## Proxy stubs and concept tests

`Concepts.hpp` contains minimal C++ structs (`ProxyPublisher`, `ProxyClient`,
`ProxyStreamerApp`, `ProxyFullCommunicatorApp`) that satisfy the concepts
**without pulling in any ROS backend**. They exist solely for static_asserts:

```cpp
static_assert(Publisher<ProxyPublisher>);
static_assert(Client<ProxyClient>);
static_assert(MessengerApp<ProxyFullCommunicatorApp>);
static_assert(CommunicatorApp<ProxyFullCommunicatorApp>);
static_assert(FullCommunicatorApp<ProxyFullCommunicatorApp>);
```

`test/test_concepts.cpp` tests both positive satisfaction and **deliberate
rejection** of bad types:

```cpp
// compile-time: build fails if concept is too permissive
static_assert(!Publisher<PubNoMessageType>);
static_assert(!CommunicatorApp<MessengerOnlyApp>);

// runtime: structured GTest output
EXPECT_FALSE((Publisher<int>));
EXPECT_FALSE((MessengerApp<ProxyStreamerApp>));
```

Both layers are present: `static_assert` catches permissive concepts at build
time; GTest gives structured output in CI.

## Communicator (the switchboard)

`Communicator` is the object every node owns. It holds four typed maps — one per
app category — each keyed by a string name:

```
messengers        : unordered_map<string, MessengerApp_VT>
communicators     : unordered_map<string, CommunicatorApp_VT>
fullCommunicators : unordered_map<string, FullCommunicatorApp_VT>
streamers         : unordered_map<string, StreamerApp_VT>
```

The value types (`MessengerApp_VT`, …) are `std::variant<unique_ptr<Backend>>`.
`unique_ptr` lets the variant hold non-movable types (e.g., `RosCommunicatorApp`
contains a `std::mutex`).

### Install / Get template methods

```cpp
template<typename C> requires CommunicatorApp<C>
STATUS InstallCommunicatorApp(const std::string & name);

template<typename C> requires CommunicatorApp<C>
C * GetCommunicatorApp(const std::string & name);
```

The concept constraint on `C` is the only gate. No data/service type parameters
appear at the call site — the app is type-agnostic at this level.

### Closed-set polymorphism

When a new backend is added, its `unique_ptr<NewBackend>` is added to the
relevant `*_VT` variant alias in `Communicator.hpp`. Dispatch uses `std::get_if`
— no virtual functions.

### Typical node setup

```cpp
Communicator comm;
comm.InstallCommunicatorApp<RosCommunicatorApp>("ros");

auto * app = comm.GetCommunicatorApp<RosCommunicatorApp>("ros");
app->Setup(argc, argv);               // rclcpp::init() — once per process
app->Login("my_node");

app->CreatePublisher<std_msgs::msg::Int32>("/topic");
auto pub = app->GetPublisher<std_msgs::msg::Int32>("/topic");
pub->Publish(msg);                    // node only sees Publisher<RosPublisher<Int32>>
```

The node never touches rclcpp types directly. `pub` is a
`shared_ptr<RosPublisher<Int32>>` but the node only depends on `Publisher<T>`.

## RosCommunicatorApp

The one concrete `CommunicatorApp` backend. Wraps `rclcpp::Node` and
`MultiThreadedExecutor`. Satisfies `CommunicatorApp<RosCommunicatorApp>` —
verified by `static_assert` at the bottom of `RosCommunicatorApp.hpp`.

### Adapters

`RosPublisher<MSG>` and `RosClient<SRV>` are thin wrappers returned by
`GetPublisher`/`GetClient`. They satisfy `Publisher<T>` and `Client<T>` by
carrying their type as a nested alias and exposing the concept API:

```cpp
template<typename MSG>
class RosPublisher {
public:
  using MessageType = MSG;            // makes Publisher<RosPublisher<MSG>> hold
  STATUS Publish(const MSG & msg);
};

template<typename SRV>
class RosClient {
public:
  using ServiceType = SRV;            // makes Client<RosClient<SRV>> hold
  bool WaitForService(nanoseconds);
  optional<SRV::Response> Request(const SRV::Request &, nanoseconds);
  STATUS AsyncRequest(req, timeout, responseCallback, timeoutCallback);
};
```

### Lifecycle

```
Setup(argc, argv)   → rclcpp::init()              (once per process)
Login(id)           → create Node + Executor, start spin thread
  …pub/sub/client/service operations…
Logout()            → cancel executor, join thread, teardown node
~RosCommunicatorApp → Logout() + rclcpp::shutdown()
```

### Spin readiness

`Login()` uses a `std::promise<void> spinStarted` to guarantee the spin thread
is inside `spin()` before returning. `Logout()` calls `cancel()` only after
`Login()` has returned — no race between start and cancel.

### Channel storage

All channels are stored type-erased by name:

```
publishers  : unordered_map<string, shared_ptr<void>>   ← RosPublisher<MSG>
subscribers : unordered_map<string, SubscriptionBase::SharedPtr>
clients     : unordered_map<string, shared_ptr<void>>   ← RosClient<SRV>
services    : unordered_map<string, ServiceBase::SharedPtr>
```

`GetPublisher<MSG>` / `GetClient<SRV>` recover the typed pointer via
`static_pointer_cast`. Type safety is the caller's responsibility (same name,
same type at creation and retrieval).

### AsyncRequest

`RosClient::AsyncRequest` fires a detached thread that waits on the future and
invokes the response or timeout callback. The future (`FutureAndRequestId`) is
move-only — it is moved into the lambda capture and the lambda is `mutable` to
allow calling non-const future methods.

---

## Process-level invariants

- `rclcpp::init` / `rclcpp::shutdown` must be paired. Two consecutive inits or
  shutdowns are not allowed.
- Exactly one `RosCommunicatorApp` per process should call `Setup()`.
- Per-test isolation: one global `Communicator` in `main()` of test executables;
  each test suite uses `Login`/`Logout` for a fresh node name.

---

## Adding a new backend

1. Implement the class and add a `static_assert(CommunicatorApp<NewBackend>)` (or
   the appropriate concept) in its header.
2. Add `std::unique_ptr<NewBackend>` to the relevant `*_VT` variant alias in
   `Communicator.hpp`.
3. No changes to `Communicator` itself — `Install`/`Get` template methods accept
   any type already in the variant.
4. The new backend must accept ROS2 interface types as communicatable data and
   handle serialization internally. Node code does not change.
